# ADR-004: Document Fields Are Aggregated Into Whole-Document Content

## Status
Accepted

## Context

The `Document` record supports structured fields (`Map<String, String>`) such as
`title`, `body`, and `summary`. When present, these fields provide a richer
content organization than a single `rawContent` string.

The question is how the indexing and search pipeline should consume these
fields. Two broad approaches are possible:

1. **Per-field indexing** — preserve field provenance through the pipeline,
   store per-field postings or vectors, and support field-aware search and
   ranking (e.g., search only in title, boost title matches).

2. **Whole-document aggregation** — treat fields as structured content sources,
   aggregate their values into a single content stream during preprocessing,
   and let the rest of the pipeline operate on the resulting unified stream.

## Decision

We have chosen **whole-document aggregation** as the current behavior.

Specifically, `DocumentPreprocessor.resolveContent()` applies the following
contract:

- If `fields` is non-empty and contains at least one non-blank value, all
  non-blank field values are joined with spaces into a single content string.
  `rawContent` is ignored in this case.
- If `fields` is empty or all values are blank, `rawContent` is used as the
  content source.
- Field names (the map keys) are not preserved past this preprocessing stage.
- The resulting `normalizedContent` is the single source consumed by lexical
  indexing, vector indexing, TF-IDF weighting, and all ranking operations.

After preprocessing, all downstream components — `InvertedIndex`, `Posting`,
`Vectorizer`, `Ranker`, `DocumentWeighter` — see one undifferentiated content
stream. There is no per-field postings list, no per-field vector, and no
field-aware scoring.

## Consequences

### Positive

- **Simplicity.** The indexing pipeline remains straightforward. All stages
  operate on a single `normalizedContent` string.
- **Consistency.** Document length, corpus statistics, BM25 normalization,
  and vector weights are all derived from the same aggregated content source.
- **Backward compatibility.** Documents without fields continue to work
  exactly as before (rawContent is used when fields are absent).
- **Fast iteration.** The current model supports experiments with structured
  input (web pages with title/body fields) without requiring a major
  architectural refactor of the index and search layers.

### Negative

- **No field-aware search.** It is not possible to restrict a query to a
  specific field (e.g., "find 'java' only in titles").
- **No field-aware ranking.** Title matches cannot be boosted relative to
  body matches.
- **No per-field term statistics.** IDF is computed globally across all
  fields; there is no notion of a term's rarity within a specific field.
- **Duplicate terms across fields.** If "java" appears in both `title` and
  `body`, it contributes twice to the term frequency, which may or may not
  be the desired behavior depending on the use case.
- **Field boundaries lost.** Phrase queries and proximity queries operate on
  the aggregated content, which means false positives can occur across field
  boundaries.

## What is intentionally not supported yet

| Feature | Status |
|---------|--------|
| Per-field indexing | Not implemented |
| Field-aware search (query by field) | Not implemented |
| Field weighting / boosting | Not implemented |
| Per-field IDF or term statistics | Not implemented |
| Per-field vector representations | Not implemented |
| Field-specific normalizer pipelines | Not implemented |

## Future extension path

When field-aware indexing becomes necessary, the following integration points
are the natural places to evolve:

1. **`DocumentPreprocessor`** — Instead of aggregating all field values into
   one string, preserve per-field token lists (e.g., `Map<String, List<String>>`).
   The preprocessing stage is the primary integration point for field
   provenance.

2. **`InvertedIndex` / `Posting`** — Add a field identifier to postings so
   that the index can distinguish which field a term appeared in. This could
   be a new field on `Posting`, or the index could be keyed by
   `(field, term)` pairs.

3. **`Ranker`** — Extend the `score()` method to accept field information.
   Field-weighted scoring (e.g., BM25F) would become possible.

4. **`DocumentWeighter` / `Vectorizer`** — Support per-field or field-weighted
   term vectors for the vector search path.

5. **`Searcher`** — Add query-time field filters or field-specific query
   parsing.

The system can also support a hybrid approach where some fields are kept
separate for filtering/sorting while others are aggregated for full-text
search. This is a common pattern in production IR systems.

## Rationale

This decision keeps the current architecture simple and consistent while the
project is still exploring core IR concepts. Structured fields provide a
clean input model without prematurely complexifying the index and search
layers. When the need for field-aware features becomes concrete, the existing
design has clear extension points.
