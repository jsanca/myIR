# ADR-005: Future Field-Aware Indexing and Field Weighting

## Status
Proposed (design exploration only — no implementation)

## Context

myIR currently supports structured document fields (`title`, `body`, `summary`,
etc.) as content sources, but the indexing model is whole-document aggregation
(see ADR-004). After `DocumentPreprocessor` joins field values into a single
`normalizedContent` string, field provenance is discarded. The inverted index,
vector store, rankers, and weighter all operate on one undifferentiated content
stream.

This ADR explores future design options for true field-aware indexing — where
the system can distinguish which field a term came from, support field-specific
search, and apply field-weighted ranking. None of these options are implemented.
This document exists to guide future decisions and prevent premature complexity.

## Current model (recap)

```
Document {title: "java", body: "java is portable"}
    │
    ▼
DocumentPreprocessor.resolveContent()
    → "java java portable"   (field names discarded)
    │
    ▼
normalizedContent = "java java portable"
    │
    ├──► LexicalIndexer → InvertedIndex → Posting(docId, tf, positions)
    │                                          (no field info)
    ├──► VectorIndexer  → DocumentVectorStore → SparseDocumentVector
    │                                                (no field info)
    └──► Corpus         → metadata.length, metadata.termFrequencies
                              (whole-document only)
```

All downstream components — `Ranker.score()`, `DocumentWeighter.weigh()`,
`CorpusStatistics.averageDocumentLength()` — operate on whole-document content.

This model is correct and sufficient for the current feature set.

## Future design options

### Option A: Field boosts during preprocessing (simplest)

Duplicate or weight terms from important fields before they reach the index.
For example, prepend title tokens twice to the aggregated content so title
terms have higher term frequency in the inverted index and vector store.

**Example:**
```
title="java"  body="java portable"
→ aggregated = "java java java portable"  (title repeated 2x)
```

**Pros:**
- Zero changes to Posting, InvertedIndex, Ranker, or Searcher.
- Works immediately with existing TF-IDF, BM25, and vector search.
- Very low implementation risk.

**Cons:**
- No field-specific search (cannot query "only in title").
- Cannot change field weights at query time.
- Inflates document length and may skew BM25 length normalization.
- Field repetition pattern must be consistent with the normalizer pipeline
  (repeated tokens still go through stop-word removal).

**Impact on components:** `DocumentPreprocessor` only.

---

### Option B: Store field name in Posting

Add a `field` attribute to `Posting` so the index records which field each
occurrence came from.

**Example:**
```
Posting(docId="doc1", tf=2, positions=[0,1], field="title")
Posting(docId="doc1", tf=3, positions=[2,3,4], field="body")
```

**Pros:**
- Enables field-specific queries (search only in title).
- Enables field-weighted scoring at query time.
- `InvertedIndex.getPostings(term)` can return all postings; the searcher
  can filter or weight by field.
- Moderate implementation effort.

**Cons:**
- `Posting` record changes ripple through many components.
- `Ranker.score()` must be extended with field awareness.
- `InvertedIndex.add()` must accept a field parameter.
- Per-field term frequencies need separate accumulation.
- `DocumentPreprocessor` must track which token came from which field during
  aggregation.

**Impact on components:**
- `DocumentPreprocessor` — must emit field-tagged tokens instead of a single string.
- `Posting` — new `field` attribute (or `Map<String, Integer>` per-field TFs).
- `InvertedIndex` — `add(term, docId, position, field)`.
- `Indexer` — `LexicalIndexer` passes field info during index population.
- `Ranker` — `score(term, posting, fieldWeights)`.
- `Searcher` — query parsing may specify fields; `SimpleSearcher` passes
  field weights to ranker.
- `Vectorizer` / `DocumentWeighter` — may need per-field weights for vector search.
- Tests — broad test additions across all changed types.

---

### Option C: Separate inverted indexes per field

Maintain one `InvertedIndex` per field (e.g., `titleIndex`, `bodyIndex`).

**Pros:**
- Clean separation — each field has its own postings and statistics.
- Natural for field-specific queries: search `titleIndex` not `bodyIndex`.
- Per-field IDF and per-field document frequencies are straightforward.
- Minimal change to `Posting` (no new field needed).

**Cons:**
- Multiple index instances to manage and query.
- Cross-field queries require merging results from multiple indexes.
- Each index must be populated separately during indexing.
- Increases memory usage (multiple `ConcurrentHashMap` instances).

**Impact on components:**
- `DocumentPreprocessor` — must produce per-field token lists.
- `Posting` — unchanged (field context is in the index, not the posting).
- `InvertedIndex` — no interface change; multiple instances used.
- `Indexer` — `LexicalIndexer` iterates per-field tokens and indexes each
  field to its corresponding `InvertedIndex`.
- `Ranker` — receives field-specific index for scoring; field-weighted scoring
  becomes merging of per-field scores.
- `Searcher` — must query one or more field indexes.
- `CorpusStatistics` — may need per-field length statistics.
- Tests — moderate additions.

---

### Option D: Fielded posting lists within a single index

Key the inverted index by `(field, term)` instead of just `term`, or nest
per-field postings under each term.

**Example:**
```
invertedIndex:
  "title" → { "java" → [Posting(doc1, ...)], "search" → [Posting(doc2, ...)] }
  "body"  → { "java" → [Posting(doc3, ...)], "engine" → [Posting(doc1, ...)] }
```

**Pros:**
- Single `InvertedIndex` instance with field awareness built in.
- Per-field postings are naturally grouped.
- Supports field-specific queries and per-field IDF without multiple index
  instances.

**Cons:**
- More complex index structure (nested maps).
- `InvertedIndex` interface changes significantly.
- `getPostings(term)` ambiguous — needs overload `getPostings(field, term)`.
- Migration from flat index to fielded index is invasive.

**Impact on components:** Similar to Option C, but concentrated within
`InvertedIndex` rather than across multiple instances. Higher interface
change cost.

---

### Option E: BM25F-style ranking

BM25F extends BM25 by computing per-field term frequencies and per-field
document lengths with field-specific boosts and saturation parameters.

**Formula sketch:**
```
score(doc, query) = Σ idf(t) × boosted_tf(t, doc) / (boosted_tf + k1 × length_norm)

boosted_tf(t, doc) = Σ_field( weight_field × tf_field / (1 - b_field + b_field × dl_field / avgdl_field) )
```

**Pros:**
- State-of-the-art field-weighted ranking.
- Different fields can have different importance (title > body > tags).
- Per-field length normalization is more accurate than whole-document length.

**Cons:**
- Requires per-field term frequencies, per-field document lengths, and
  per-field average lengths.
- `CorpusStatistics` must track per-field metrics.
- Implementation is significantly more complex than Options A-C.
- Best built on top of Option B, C, or D (field provenance must exist first).

**Impact on components:**
- `DocumentPreprocessor` — must produce per-field lengths.
- `Posting` — must carry per-field TFs (or multiple postings).
- `InvertedIndex` — field-aware (via B, C, or D).
- `Ranker` — `Bm25Ranker` replaced or extended with `Bm25FRanker`.
- `CorpusStatistics` — per-field document lengths and averages.
- `Searcher` — must pass field weights to ranker.
- Tests — extensive additions.

---

## Recommended incremental path

A big-bang refactor to full field-aware indexing is premature. The following
phased approach keeps each step small and testable:

| Phase | Scope | Prerequisite |
|-------|-------|-------------|
| **1. Stabilize** | Keep current whole-document aggregation stable. Document the contract (done — ADR-004, tests). | None |
| **2. FieldKey semantics** | Define canonical field names (`FieldKey.TITLE`, `FieldKey.BODY`, etc.) and a `FieldMap` abstraction if the free-form `Map<String, String>` becomes limiting. | Phase 1 |
| **3. Preserve provenance** | Update `DocumentPreprocessor` to emit per-field token lists alongside the unified `normalizedContent` for backward compatibility. No downstream changes yet. | Phase 2 |
| **4. Field-aware postings** | Choose Option B or C to add field information to the index. `InvertedIndex` gains field awareness. Lexical search becomes field-aware. | Phase 3 |
| **5. Simple field boosts** | Implement Option A at the `DocumentPreprocessor` level (field repetition) or query-time boosts via the ranker. Minimal index changes. | Phase 3 or 4 |
| **6. BM25F ranking** | Implement Option E on top of field-aware index structures. Per-field statistics in `CorpusStatistics`. Field-weighted `Bm25FRanker`. | Phase 4 |

Phases 2-4 can be implemented incrementally, with each phase adding value
before the next begins. Phase 6 is the most complex and should only be
undertaken when the simpler field-aware infrastructure is stable and the
need for sophisticated field weighting is demonstrated.

## What is intentionally not implemented now

- Field-aware postings (no field attribute on `Posting`).
- Per-field inverted indexes (single `InvertedIndex` for all content).
- Field-specific queries (no `Searcher.search(field, query)`).
- Field weighting or boosting in ranking.
- Per-field document length or corpus statistics.
- BM25F or any field-weighted ranker.
- Field-aware vector representations.

The current architecture is deliberately simple. When the need for field-aware
features becomes concrete, this ADR provides a menu of options and a phased
path to follow.
